# LangChain and Claude: can it pass effort and fallbacks to Opus 5.5?

Research for issue Rez-1/component-migration-agent#4. Checked 2026-11-09.

**Question.** Does the current `langchain-anthropic` (`ChatAnthropic`) support what the repair loop needs on Claude Opus 5.5 (`claude-opus-5-5`)? And if it has gaps, how do we keep the model swappable and still call the Anthropic SDK where we need to?

**Short answer.** `ChatAnthropic` 1.7.10 supports six of the seven features. Effort, adaptive thinking, caching, cache-token usage and strict tools are native. `fallbacks` works through `model_kwargs`. The **Message Batches API is not supported at all**, and Batches is the biggest cost lever for a €20/month budget. Recommendation: put our own small `RepairModel` interface in front of the model. The default adapter calls the `anthropic` SDK directly, and an optional adapter covers other providers through LangChain's `init_chat_model`. Details are under [Recommendation](#recommendation).

### Notes behind the table

- **Effort default.** Opus 5.5 defaults to `medium` when `effort` is omitted ([Anthropic effort docs](https://platform.claude.com/docs/en/build-with-claude/effort)). LangChain sends nothing unless we set it, so to get our `low` default we must pass `reasoning_effort="low"` explicitly. LangChain's model profile has `reasoning_effort_default = "medium"` for Opus 5.5 (`data/profile_augmentations.toml`), but that value is metadata only. It is not sent with requests.
- **Auto `display: "summarized"`.** Setting effort makes LangChain send `thinking={"type":"adaptive","display":"summarized"}`. This is valid on Opus 5.5 and billed the same as omitted display. It does put summarized thinking blocks into the `AIMessage` content, so our state and logs will be larger.
- **Passing `fallbacks`.** `ChatAnthropic(model="claude-opus-5-5", betas=["server-side-fallback-2026-07-01"], model_kwargs={"fallbacks": "default"})`. A bare `fallbacks=` constructor kwarg is also moved into `model_kwargs` (with a warning) by `_build_model_kwargs` ([CM#L1706](https://github.com/langchain-ai/langchain/blob/langchain-anthropic%3D%3D1.7.10/libs/partners/anthropic/langchain_anthropic/chat_models.py#L1706)). Don't confuse it with LangChain's own `Runnable.with_fallbacks()`, which is a client-side retry on exceptions and never sees a refusal, because a refusal arrives as HTTP 200. I read this path in the code but did not run it, since the brief allowed no API calls.
- **Spotting a fallback.** Anthropic says to check the top-level `model` field and look for a `fallback_message` entry in `usage.iterations`; a `fallback` content block marks the handoff ([docs](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback)). With LangChain this is `response_metadata["usage"]["iterations"]`, which is untyped and not in `usage_metadata`. LangChain passes unknown content blocks such as `fallback` back to the API unchanged ([CM#L964–967](https://github.com/langchain-ai/langchain/blob/langchain-anthropic%3D%3D1.7.10/libs/partners/anthropic/langchain_anthropic/chat_models.py#L964-L967)). I have not checked that the API accepts a replayed `fallback` block, so that is unverified.
- **Fallbacks and batches don't mix.** Quote from the Anthropic docs: *"The `fallbacks` parameter is not supported on the Message Batches API (a batch item that includes it comes back as an errored result)."* Refusals inside batches need our own retry.
- **Caching prices for Opus 5.5.** Base input is $4/MTok. 5-minute cache writes cost 1.25× ($5), 1-hour writes 2× ($8), and reads 0.05× ($0.20). The minimum cacheable prefix is 512 tokens. These multipliers stack with the 50% Batch discount ([prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). In batches, cache hits are "best-effort" (30–98%), and the docs recommend the 1-hour TTL ([batch docs](https://platform.claude.com/docs/en/build-with-claude/batch-processing)).
- **Batches with Opus 5.5.** Supported. The docs list `claude-opus-5-5`, with results available within 24 hours and most batches finishing in under 1 hour. The forced-`tool_choice` 400 also applies inside batches. `max_tokens: 0` (cache pre-warming) is rejected in a batch.

## Surprises and risks

1. **SDK major-version drift (highest risk).** `langchain-anthropic` sets no upper bound on `anthropic`, but its CI lock pins **1.1.0**, and its compat layer only describes the 0.x and 1.x SDKs (`_sdk_compat.py`). A fresh `uv add langchain-anthropic` installs **anthropic 2.6.0**. That release sends API version `2026-10-21`, which rejects `temperature`/`top_p`/`top_k` on every model and changes some SDK behaviour (Bearer auth among others, per [the 2026-10-21 migration guide](https://platform.claude.com/docs/en/api/migration-2026-10-21)). I have not verified that LangChain works on 2.x. If we use LangChain, pin `anthropic<2` or add a smoke test.
2. **The Opus 5.5 guards are incomplete.** LangChain catches `thinking: disabled` and sampling params ahead of time for Fable and Sonnet 5.5, but not for Opus 5.5. It also only drops a forced `tool_choice` when `thinking` was set explicitly. Generic "swappable" code that sets `temperature=0` or `tool_choice="any"`, which is common in LangChain examples, will get a 400 on Opus 5.5. The provider abstraction doesn't protect us here.
3. **Refusal handling is changing.** A commit merged on master after 1.7.10 ([#41715](https://github.com/langchain-ai/langchain/pull/41715)) makes `with_structured_output` raise `ModelRefusalError` on refusals. 1.7.10 itself added standard refusal content blocks (langchain-core ≥1.7.5). Any refusal path that depends on LangChain behaviour may change between patch releases.
4. **The budget feature is the missing one.** At $4/$20 per MTok, the two cost levers are caching (native in LangChain) and Batches (missing). Batches halve the cost for runs that aren't interactive, such as eval sweeps and full-repo repair passes, so the SDK is needed for at least that path.
5. **Cache hits need byte-identical requests.** If synchronous calls go through LangChain and batch calls through the SDK, two different code paths build the request. Any difference in tool JSON, the system prompt or block order changes the prefix and loses cache hits. This is a strong argument for a single request builder.

## Recommendation

**Define our own small interface and make the Anthropic SDK the default adapter. Don't make `BaseChatModel` the seam.**

```python
class RepairModel(Protocol):
    def complete(self, req: RepairRequest) -> RepairResult: ...
    def submit_batch(self, reqs: list[RepairRequest]) -> BatchHandle: ...   # optional capability
    def collect_batch(self, handle: BatchHandle) -> dict[str, RepairResult]: ...
```

- `RepairRequest` is provider-neutral: system prompt, messages, tool specs, an effort level (`low`/`medium`/`high`) and a cache hint. `RepairResult` holds text, tool calls, stop reason (`refusal` included), the model that served it, and token usage including cache reads and writes.
- **`AnthropicRepairModel`** uses `anthropic` directly. One `build_params()` produces `messages.create` params *and* batch `params`, so cached prefixes are identical on both paths. Synchronous calls send `output_config.effort`, `cache_control`, strict tools with `tool_choice: auto`, `betas=["server-side-fallback-2026-07-01"]` and `fallbacks="default"`. Batch calls leave out `fallbacks` and handle `refusal` results with their own retry. It reads `usage.iterations` for fallback accounting. It never sends `thinking` or `temperature`.
- **`LangChainRepairModel`** (optional, added when someone actually wants another provider) wraps `init_chat_model(...)`, maps the effort level to that provider's knob, and returns `NotImplemented` for `submit_batch`, so the graph falls back to synchronous calls.
- LangGraph doesn't need a LangChain chat model: a graph node can call `RepairModel.complete()` like any other function. That keeps the "swappable" promise at the level that matters, the repair loop, without inheriting LangChain's gaps on the default path.

**Why not "LangChain with passthroughs"?** It works for features 1–6 today: `ChatAnthropic(reasoning_effort="low", betas=[...], model_kwargs={"fallbacks": "default"})` plus `bind_tools(strict=True)` and `cache_control=`. But Batches still needs the SDK, so we'd have two request builders anyway (risk 5). The swappability would also be thin: effort, fallbacks, cache breakpoints and strict tools are each configured differently per provider, so the swap point would be full of Anthropic-specific kwargs either way. On top of that we'd carry the SDK pin and guard-gap risks (1, 2). If the team still prefers LangChain as the seam, the minimum is: pin `anthropic<2`, set `reasoning_effort="low"` explicitly, never set `temperature`/`thinking`/forced `tool_choice`, and add a separate SDK-based batch path that shares a request builder.
